# Project plan

Магазин. Один монолит. Папки по фичам. Внутри фичи три слоя: вход (`http` / worker / cron / sse) → `service` → `repo`.

Транзакции не отдельный слой, а механизм внутри `orders`. Пользователи отдельная фича. ClickHouse не заменяет Postgres и в позвоночник не входит.

## Что строишь

Пользователь кладёт товар → заказ создался → его собрали → статус «в доставке» / «готов».

Критерий, что позвоночник готов:

- двойной клик не плодит два заказа
- воркер можно убить, заказ не теряется
- список заказов без N+1
- в логе заказ находится по `id`

Пока критерий не закрыт, SSE, чат, Kafka, ClickHouse, Grafana, кубер и WebTransport не трогаешь.

## Архитектура

До конца учёбы один монолит. Три деления это не три сервиса, а два разреза в одном процессе.

По фичам: `users`, `catalog`, `orders`, `shared`. Позже папкой, не репозиторием: `analytics`. Чат поддержки исключение: отдельный сервис после позвоночника.

Внутри фичи три слоя не меняются, когда появится SSE, сокет, Kafka, ClickHouse или Grafana. Меняются только входы и выходы:

- HTTP / cron / воркер / SSE / сокет зовут `orders.service`
- Postgres одна
- Rabbit и Kafka трубы в `shared`, пишет туда не контроллер, а `service` / outbox
- ClickHouse читает аналитика, не оформление заказа

Не дроби на микросервисы потому что Kafka или ClickHouse. Не добавляй четвёртый слой `domain` / `use-case` / `interactor`. Не выноси catalog в отдельный деплой.

Резать на два сервиса имеет смысл только если уже упёрся: разные релизы, разный скейл, команда мешается. Сейчас этого нет.

### Пользователи

Тонкая фича: регистрация, логин, сессия или JWT. Без неё нет «моих заказов» и проверки IDOR. Это не identity-платформа.

`shared/auth.ts` отвечает на вопрос «кто ты». `users/` хранит пользователя. Проверка «этот заказ твой» живёт в `orders.service`.

### Транзакции

Папки `transactions/` нет. `BEGIN` / `COMMIT` вокруг «списать склад + записать заказ» в `orders.service` + `orders.repo`. Либо оба шага прошли, либо ни одного.

### Кэш

Витрина в Redis. Заказы не кэшируешь. Иначе это не «добавил кэширование», а баги согласованности без учебной выгоды.

## Каркас

Чат поддержки в этот каркас не кладётся. Отдельный сервис, отдельный процесс. Магазин отдаёт ему только `order_id` и факт владения.

## Стек позвоночника

| Что берёшь           | Зачем в этом проекте                    | Куда кладёшь                                       |
| -------------------- | --------------------------------------- | -------------------------------------------------- |
| Postgres             | Заказ + склад атомарно                  | `shared/db`, вызывают repo                         |
| Express + TypeScript | HTTP-вход                               | `app.ts`, `*.routes.ts`                            |
| Redis                | Идемпотентность оформления, кэш витрины | `shared/redis`, зовут catalog/orders service       |
| RabbitMQ             | Работа после ответа клиенту             | `shared/rabbit`, пишет service, читает `worker.ts` |
| Cron                 | Добить зависшие `pending`               | `cron.ts` → `orders.service`                       |
| Swagger              | Контракт API                            | рядом с routes                                     |
| Vitest               | Шаги 3–8 проверяются тестом             | `tests/`                                           |

## Позвоночник, по шагам

Каждый шаг закрывается проверкой. Следующий не начинаешь, пока проверка красная.

### Шаг 0. Скелет

Docker Compose поднимает Postgres, Redis, Rabbit. TypeScript собирается. `http.ts` отвечает на health. Swagger пустой, но подключён. Vitest гоняет один smoke-тест.

Проверка: `compose up`, health 200, один тест зелёный.

### Шаг 1. Пользователи

Регистрация и логин. Защищённый эндпоинт без заказа ещё не нужен, достаточно «кто я». Без этого шага IDOR потом проверять нечем.

Проверка: логин выдаёт сессию, без сессии защищённый эндпоинт закрыт.

### Шаг 2. Каталог

Товары и остаток на складе. Список витрины. Короткий кэш витрины в Redis. Инвалидация кэша при изменении остатка. Заказы сюда не кладёшь.

Проверка: витрина отдаётся из кэша при повторном запросе, после смены остатка кэш не врёт.

### Шаг 3. Создание заказа

`POST /orders`: в одной транзакции списать товар и записать заказ. Нет товара, нет заказа. Есть заказ, склад уменьшился. Это учебное ядро Postgres.

Проверка: обрыв после списания склада не оставляет дыру. Повтор без идемпотентности пока может создать второй заказ, это нормально, это шаг 5.

### Шаг 4. Список заказов без N+1

`GET /orders`: 20 заказов, у каждого позиции. Один запрос на заказы, один на все позиции. Не 20 доп. запросов. Смотришь это в логе SQL, не на глаз.

Проверка: в логе SQL два запроса на список, не 21.

### Шаг 5. Идемпотентность

Двойной клик «оформить». Ключ в Redis, например `order:user:123:idem`. Второй клик не создаёт второй заказ. Учебный вариант: Redis как быстрый замок. Правда навсегда всё равно в Postgres, уникальность или повтор того же ответа.

Проверка: два одинаковых `POST /orders` подряд дают один заказ.

### Шаг 6. Rabbit

После коммита заказа HTTP сразу отвечает. Воркер делает побочки: письмо, накладная, смена статуса на «собирается». HTTP не ждёт 5 секунд. Воркер убил, сообщение не ack, после рестарта заказ дожимается, не теряется.

Проверка: убил `worker.ts` на середине, поднял снова, заказ не потерян и не обработан дважды без защиты.

### Шаг 7. Cron

Раз в минуту: `pending` старше 10 минут либо добить, либо пометить `failed`.

Проверка: заказ, зависший 11 минут, меняет статус без ручного запроса.

### Шаг 8. Дыры и логи

Чужой `GET /orders/999` не отдаёт чужой заказ. Карту и токен в лог не пишешь. В каждой записи есть `request_id`, после создания заказа ещё `order_id`. По `order_id` находишь всю цепочку.

Проверка: пользователь A не читает заказ B. По `order_id` в логе видна цепочка от HTTP до воркера.

### Шаг 9. Стресс

Долбишь `POST /orders` и `GET /orders`. Смотришь, где тормозит список (снова N+1) или воркер не успевает. Это не отдельный продукт, это проверка шагов 4 и 6.

Проверка: позвоночник закрыт по критерию из начала плана.

## Надстройки

Тот же монолит, кроме чата. Порядок такой, не параллельно.

### 1. SSE на статус заказа

Страница заказа подписана на статус. Источник правды тот же `orders.service`. Сокет сюда не тащишь.

Проверка: смена статуса в воркере приходит на открытую страницу без перезагрузки.

### 2. Чат поддержки на WebSocket

Отдельный маленький сервис, не папка в магазине. Магазин отдаёт только `order_id` и факт, что пользователь его владелец. Чат хранит сообщения, не заказы и не склад. Общая авторизация. Общая проверка «этот user владеет этим order». Отдельный деплой ради учебы интеграции, не ради микросервисной религии.

Проверка: чужой пользователь не пишет в чужой заказ. Магазин при убитом чате всё ещё принимает заказы.

### 3. Kafka рядом с живым Rabbit

Rabbit остаётся очередью задач, воркер заказа. Kafka это журнал событий: заказ создан, статус сменился, аналитика может перечитать. Пишет снова `orders.service` / outbox, не контроллер. Не заменяй Rabbit на Kafka. Не режь монолит потому что Kafka.

Проверка: новый потребитель перечитывает старые события. Воркер накладных по-прежнему на Rabbit.

### 4. ClickHouse

Аналитика, не источник правды. Postgres отвечает на «этот пользователь, этот заказ, этот остаток». ClickHouse отвечает на «за сегодня, по всем, сгруппируй».

Поток: `orders.service` пишет заказ в Postgres и событие в outbox → Kafka несёт факты → папка `analytics` кладёт их в ClickHouse. HTTP магазина ClickHouse не спрашивает на `GET /orders` и на оформление.

Что считать: заказы по статусам и времени, воронка pending → собран → доставка, популярность товаров, задержка воркера. Что не тащить: текущий сток как правду, сессии, пароли, идемпотентные ключи, тело чужого заказа.

Без Kafka кормить кроном из Postgres можно. Для учёбы это слабее. Основной путь: событие → Kafka → ClickHouse.

Проверка: оформление заказа не ходит в ClickHouse. Агрегат «заказов за час» сходится с Postgres, но запрос идёт в ClickHouse.

### 5. Логи: Loki + Grafana

Тот же `request_id` → `order_id`. Grafana это не фича магазина, это смотрелка. Два источника: Loki это логи, ClickHouse это агрегаты. «Почему этот заказ завис» ищешь в логе по `order_id`. «Сколько pending за час» берёшь из ClickHouse.

Проверка: в Grafana находится цепочка одного заказа и график по статусам.

### 6. Kubernetes

Когда приложение уже умеет http + worker + cron тремя процессами. Кубер учит запускать то же самое тремя Deployment, не переписывать домен.

Проверка: три процесса поднимаются манифестами. Убийство пода воркера не теряет заказ, как на шаге 6.

### 7. WebTransport

По фану, после сокета. Не вместо SSE статуса.

## Аналоги

На позвоночнике аналоги не ставишь. Читаешь, чтобы знать, что меняется, если заменить деталь.

**База.** Postgres. Аналоги: MySQL (тоже SQL и транзакции, другой диалект и MVCC), SQLite (удобно в тесте, не прод-склад), MongoDB (документ, транзакции слабее учат склад + заказ). Для этого проекта Postgres правильный: учебная единица это одна транзакция на двух таблицах.

**HTTP-фреймворк.** Express. Аналоги: Fastify (схема и скорость из коробки), Koa (то же middleware, меньше батареек), Nest (модули и DI, легко уехать в четвёртый слой), Hono (легче, чаще на edge). Express оставляешь, чтобы три слоя были твоими, а не рамкой фреймворка.

**Кэш / замок.** Redis. Аналоги: Memcached (только кэш, нет структур под idem-ключ), KeyDB / Valkey (совместимый протокол, другая эксплуатация). Redis Streams это уже очередь, не кэш. Для витрины и короткого замка Redis. Для правды заказа нет.

**Очередь задач.** RabbitMQ. Аналоги: Redis Streams (уже есть Redis, слабее гарантии), облачная очередь вроде SQS (мало маршрутизации), NATS (проще, другая модель). Kafka в аналоги очереди не клади: это журнал, не воркер накладных.

**Журнал событий.** Kafka. Аналоги: Pulsar. Очередь удаляет сообщение после ack. Журнал хранит и даёт перечитать.

**Аналитика.** ClickHouse. Аналоги: TimescaleDB / агрегаты в Postgres (проще эксплуатация, хуже широкие сканы), Druid (тот же класс, тяжелее в учебе), BigQuery / Snowflake (облако), Elasticsearch (поиск и логи, не колоночная аналитика заказов). Postgres из-за ClickHouse не выкидываешь.

**Расписание.** Процесс `cron.ts`. Аналоги: системный crontab, repeatable-джобы в Bull/BullMQ, `pg_cron`. Для монолита отдельный entry проще убить и поднять, как воркер.

**Документация API.** Swagger UI поверх OpenAPI. Аналоги: Redoc, Scalar. Формат один, OpenAPI. Меняется только отрисовка.

**Тесты.** Vitest. Аналоги: Jest (тяжелее, привычнее в старых гайдах), `node:test` (без лишней зависимости).

**Пуш статуса.** SSE. Аналоги: long polling, WebSocket, WebTransport. Статус заказа это сервер → клиент, без чата. SSE здесь точнее сокета.

**Чат.** WebSocket. Аналоги: SSE не тянет нормальный двусторонний чат, WebTransport позже как эксперимент.

**Логи.** Loki + Grafana. Аналоги: ELK (Elasticsearch + Kibana), Grafana Tempo (трейсы, не логи), Prometheus (метрики). Сначала логи с `request_id`, потом куда их складывать.

**Оркестрация.** Kubernetes. Аналоги: тот же Docker Compose (уже есть), Nomad, systemd на одной машине. Кубер имеет смысл, когда процессов уже три.

## Чего не делать

- Не кэшировать заказы в Redis и не класть их правду в ClickHouse.
- Не делать `users` микросервисом.
- Не делать `transactions/` папкой.
- Не писать в Rabbit, Kafka или ClickHouse из контроллера.
- Не тащить чат в `orders/` и не тащить склад в чат.
- Не подключать Kafka, пока Rabbit не переживает убийство воркера.
- Не подключать ClickHouse, пока Kafka не умеет отдать событие новому потребителю.
- Не резать монолит, пока нет разных релизов, разного скейла или мешающейся команды.
